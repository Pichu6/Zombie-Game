# The renderer, at engineering level

**Date:** 2026-10-08. **Status:** research note, not a decision. **Feeds:** [0002](../decisions/0002-engine-stack.md), [0003](../decisions/0003-clothing-wrap.md), [engine architecture](../design/engine-architecture.md), [art direction](../design/art-direction.md), [cameras and modes](../design/cameras-modes.md), [zoom continuum](../design/zoom-continuum.md), [spec 16](../tier0/specs/16-view-2d.md). **Evidence:** primary sources read from git clones: KhronosGroup/Vulkan-Guide @ f71c596 (2026-09-27), KhronosGroup/Vulkan-Samples @ 177edeb, SaschaWillems/Vulkan @ aa8fde2, GPUOpen VulkanMemoryAllocator @ v3.4.0 (3aa9212), zeux/meshoptimizer @ 4195af6 (after v1.3), zeux/niagara @ b1ecec1, charles-lunarg/vk-bootstrap @ 558b002, turanszkij/WickedEngine @ 707d007 (shaders only), Unity-Technologies/Animation-Instancing @ 13a820d, pezcode/Cluster @ a25ff32, Angelo1211/HybridRenderingEngine @ 67a0304, DaveH355/clustered-shading @ 3589aef, wojtekpil/Godot-Octahedral-Impostors @ 706e9a5; SDL `SDL_gpu.h` and Dear ImGui backends at the commits our CMake pins. The Olsson, Billeter and Assarsson paper (HPG 2012) and the NVIDIA Skinned Instancing whitepaper were blocked; their numbers come from search summaries (`reported`). Nothing was built or run on a GPU: every cost for our game below is arithmetic or judgement. **IDs:** RN.

[0002](../decisions/0002-engine-stack.md) plans a small renderer of our own on Vulkan (clustered forward; skinning, morphs and the clothing wrap in compute; vk-bootstrap, VMA, meshoptimizer). This note answers what that renderer looks like in 2026 terms, what it costs for hundreds to thousands of pops, and what the 2D window needs now.

## 1. A minimal Vulkan 1.3 renderer for this game

What niagara (RN-12 to RN-17) and the Khronos material (RN-1 to RN-11) agree on, scaled to our needs:

| Part | Choice | Why |
| --- | --- | --- |
| Baseline | Vulkan 1.3 with BDA, descriptor indexing, dynamic rendering, synchronization2, drawIndirectCount, scalar layout, 16-bit storage | All core in 1.2/1.3 (RN-1, RN-2); niagara's list (RN-14) minus mesh shaders, ray tracing and descriptor heaps |
| Setup | vk-bootstrap for instance, device, queues and swapchain; SDL3 for the window and `SDL_Vulkan_CreateSurface` | RN-39 |
| Frames | 2 frames in flight, 3 swapchain images. Per frame: acquire semaphore, command pool per recording thread, upload ring. Per swapchain image: present semaphore | RN-7, RN-10, RN-11, RN-12 |
| CPU-GPU sync | One timeline semaphore on the graphics queue for "frame N done" (replaces fences); binary semaphores only for acquire and present; present fence from swapchain_maintenance1 where available | RN-8, RN-9 |
| Passes | A fixed list in one function: upload, skin/morph/wrap (compute), cull and LOD (compute), shadow depth, depth prepass, cluster build and light assignment (compute), forward opaque, transparent, post (tone map), UI (ImGui), present | RN-12, RN-26, RN-36 |
| Barriers | A helper for global memory barriers between named stages; image barriers only for layout changes; GENERAL layout where unified layouts are supported | RN-6, RN-13 |
| Render graph | No. A dozen passes known at compile time do not need one; niagara ships 30 barriers by hand. Revisit if passes become data-driven | RN-12 |
| Bindless | One global descriptor set: arrays of sampled images and samplers (descriptor indexing, update after bind); all buffers by device address in push constants or a per-draw record | RN-2, RN-4; descriptor heap later (RN-5) |

## 2. Skinning, morphs and the clothing wrap

The pipeline of [CW-8](clothing-wrap.md) maps onto RN-31 almost line for line:

1. **One compute dispatch per body, one thread per vertex:** base position, plus morph deltas (weights from the body simulation), then the bone blend, then write position, normal and tangent to an output buffer. Wicked Engine does exactly this (RN-31). Because every body shares one topology ([CW-19](clothing-wrap.md)), the morph and skin-weight data are shared; a body owns only its weights, its bone palette (RN-41) and its output buffer (RN-42).
2. **Sparse morphs.** Wicked stores dense deltas and loops over active targets per vertex. With about 100 body morphs, the efficient form is per-morph sparse lists (RN-43): either a gather (each vertex reads a short list of (morph, delta) pairs) or a dense pass only for the few morphs with non-zero weight. Body morphs change slowly (hunger over weeks), so the morphed rest shape can be **cached per body** and recomputed only when weights move; per frame only the skinning runs. That is an estimate of a large saving, not measured.
3. **Wrap passes** after skinning, one per clothing layer ([0003](../decisions/0003-clothing-wrap.md)), reading the previous layer's output as their body.
4. **Draw** reads the output buffers by device address like any static mesh, so shadows, depth prepass and the main pass share one skinning result (the reason to skin in compute rather than in the vertex shader of RN-30).
5. **Sync:** one compute-to-vertex barrier after all skin and wrap dispatches. One output buffer per body is enough if the frame's compute and draws are on one queue: the barrier at the start of the next frame's compute orders it after the previous draws. A second copy is needed only for motion vectors (RN-42).
6. **LOD:** coarse LODs are index buffers over a prefix of the same vertex buffer (RN-18), so a distant body can skin only that prefix. Use `SimplifyRegularize` for skinned LODs (RN-19). Meshlet culling does not apply to skinned bodies as built (RN-21).

The numpy reference ([wrap_reference.py](../../tools/garment/wrap_reference.py)) stays the specification for the wrap shader; the same approach (a CPU reference compared vertex by vertex) should be used for the skin-and-morph shader.

## 3. Lights: what clustered forward handles

Clustered forward has been shown with thousands of lights (RN-28, RN-29). Our scenes need tens. The practical limits are elsewhere:

- **Per-cluster cap** (RN-27): lights beyond it vanish silently. Use a compact list with an offset and count per cluster, and count overflows in a debug overlay. The "everything visible matches a real state" rule ([art direction](../design/art-direction.md)) makes a dropped light a correctness bug.
- **Shadows** are the budget (RN-45): the sun or moon with cascades, plus a few shadowed point or spot lights chosen by importance (the player's torch, fires), the rest unshadowed.
- **The simulation's light field is not the renderer's lights.** Stage 6 already computes lux per cell. The renderer draws the lamps the simulation says are on; it never computes what a pop can see. Perception stays in the simulation ([cameras](../design/cameras-modes.md): transparency never changes perception).

## 4. Crowds: hundreds to thousands of pops

One body model in the simulation does not mean one drawing method. Tiers by screen size, matching the height bands of the [zoom continuum §3b](../design/zoom-continuum.md):

| Tier | When | How it is drawn | Rough budget (estimate) |
| --- | --- | --- | --- |
| Full | Near, hot bodies | Compute morph + skin + clothing wrap, full LOD (section 2) | about 50 at once (RN-42) |
| Mid | Street distance | Compute skin of a coarser LOD prefix; clothing baked into the body texture when gear changes ([CW-17](clothing-wrap.md)); morph rest shape cached | hundreds |
| Far | District | Baked-animation instancing (RN-32, RN-33): a few locomotion clips in a texture, one instanced draw per LOD, CPU sends only clip and frame | thousands |
| Marker | City and up | A dot or icon at minimum screen size, a keyed sample of real pops ([zoom continuum](../design/zoom-continuum.md)) | capped by screen |

GPU culling with indirect count (RN-16) drops off-screen instances without CPU work. Octahedral impostors (RN-34) suit buildings and trees in the City view, not people. Moving between tiers needs a cross-fade over a range of distances, as the zoom continuum already requires.

## 5. The 2D top-down view: now and later

**Now (Tier 0, [spec 16](../tier0/specs/16-view-2d.md)):** SDL_Renderer and ImGui draw lists are the right tool (RN-35 says so for simple 2D, and RN-36 removes the 64k-vertex limit). The block is a few thousand rectangles. Nothing here needs Vulkan. What the user reported ("WASD is poor, hard to tell what is going on") matches RN-40: positions jump between cell centres at tick rate and stacked walkers hide each other. That is view-side smoothing ([engine architecture §3](../design/engine-architecture.md), [second-order dynamics](second-order-dynamics.md)), not renderer work.

**Later (when the 3D renderer starts):** the top-down view becomes one camera of the Vulkan renderer. Tactical and management cameras are orthographic and tilted ([cameras](../design/cameras-modes.md)), drawing the same meshes with the crowd tiers of section 4. ImGui moves to its Vulkan backend with dynamic rendering (RN-36). Keep the `--shot` offscreen path: a headless render to an image is how renderer changes get checked without a screen (a passing test is not visual validation, so the shot goes to the user).

**In between:** the SDL3 GPU API (RN-35) could carry a richer 2D or 2.5D view (instanced sprites, a light overlay in a shader) without our own Vulkan code. It cannot carry the 3D plan (no bindless, no device address), so it would be thrown away. Recommendation: do not use it; stay on SDL_Renderer until the Vulkan renderer starts.

## What this means for us (Proposal)

1. Keep [0002](../decisions/0002-engine-stack.md) as written, with these specifics: baseline Vulkan 1.3 with the feature list of section 1; vk-bootstrap, VMA, meshoptimizer; **no render graph**; bindless by descriptor indexing plus buffer device address; 2 frames in flight; timeline semaphore for frame pacing.
2. The first renderer milestone is the one [clothing-wrap](clothing-wrap.md) names: one body with morph and skin in compute plus a wrapped T-shirt and a live fat slider. Add a CPU reference for skin and morph next to the wrap reference, compared vertex by vertex.
3. Write the frame loop with the RN-7 fix (present semaphores per swapchain image) from day one, and run synchronization validation in CI on a software or headless device before any visual check.
4. Crowds by tiers (section 4). The "visible population density" question in [art direction](../design/art-direction.md) gets a starting budget: about 50 full bodies, hundreds mid, thousands far, markers above.
5. The renderer draws lights the simulation reports and never feeds perception back. Light overflow and dropped instances show in a debug overlay.
6. Tier 0 window: fix legibility in the view (interpolation, stacked walkers), no GPU API change.
