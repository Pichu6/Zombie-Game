# Simulation scale in other games

**Date:** 2026-10-06. **Status:** research note, not a decision; nothing here is Decided, Implemented or Validated by us. **Feeds:** [pop continuity](../design/pop-continuity.md), [spec 28](../tier0/specs/28-pop-levels.md), [0033](../decisions/0033-restoring-cost-and-two-way-projects.md). **Evidence:** web search on 2026-10-06; direct page fetches were blocked by the proxy for most sites (Dwarf Fortress wiki, Paradox, Colossal Order, Steam, Nexus, Project Zomboid), so every figure comes from a search-result excerpt of the cited page, not a full read. Many sources are player posts or mod pages, not developer statements; the table says which. Treat all numbers as reported and re-check the primary page before relying on one. **IDs:** SS.

It feeds the open question in [pop continuity](../design/pop-continuity.md) (lazy / record / embodied pops).

## Lessons for us

- **Everyone keeps a small tracked set and abstracts the rest.** DF tracks "a small percentage" because of memory; Bannerlord keeps heroes and turns troops into counts. Our three levels fit this; the open question is only the size of the middle (record) tier.
- **Cost follows object count, not people.** Victoria 3's slowdown tracked the number of pop objects, not the population. Our budget should count records and embodied bodies, never "population".
- **Split record, unit and live agent.** Cities: Skylines 1 holds 1,048,576 citizens but only 65,536 walking instances. Lazy / record / embodied is the same idea; its id width (16 bits) was a hard memory choice worth copying consciously.
- **Culling is a design feature, not a patch.** CK3 deletes unimportant dead characters; DF culls unimportant dead histfigs; RimWorld needs mothballing or world pawns pile up and slow ticks. We need an explicit rule for when a record collapses back to lazy (seed only) and for what is kept after death.
- **A hidden cost is cross-checking everyone against everyone.** DF's frame loss is blamed on line-of-sight checks across all creatures, not pathfinding (about 6% of a tick in one profile). Embodied pops must only perceive other embodied things nearby.
- **Event-heavy AI costs more than state.** CK3 reporting says most cost is AI decisions and events. Record-level pops should update on a schedule or on events, not every tick.
- **Zombies as per-cell counts is proven.** Project Zomboid keeps unloaded zombies as numbers per cell and moves the numbers. Our dead can use that until they are embodied.
- **Keep a followed-person log.** CS2 shows a lifepath journal per citizen is cheap because it is stored events, not simulation. Leaders and followed pops can store events, then replay or summarise them.

## Numbers to use as a first budget (estimates)

All of these are our estimates, not found in sources, except where a source is named. They need measurement with `zs --bench` before use.

| Item | First budget | Basis |
| --- | --- | --- |
| Embodied pops at once | 50-300 | DF fort realistic limit 200-250 (source in table); our own bench ran 4 pops + 60 walkers for a game day in about 0.2 s ([status](../status.md)). |
| Record pops (stored) | 10,000-100,000 | CK3 reports 35,000 living characters playable; DF cap token example 15,000 and max 100,000 (see table). |
| Lazy pops | No stored cost; limited by generation speed only | FM keeps 750,000+ people; CS1 keeps over a million citizen records. Per-person memory at each level: not found. |
| Record size | Aim for a few hundred bytes to 1 KB | Pure estimate; no source states per-person bytes. CS1 instance id is 2 bytes (source in table), which shows ids and not objects are the lever. |
| Embodied cost | Measure, not assume | Not found in sources. |
| Zombies | Count per cell while unloaded; real bodies only near the player | Project Zomboid: 52,000 at start, 150,000 at peak (player source). |
| Record update rate | Event-driven or a few times per game day | Estimate. Victoria 3 ticks 6 game-hours (source in table). |
