# Data compression for saves, replays, traces and pop records

**Date:** 2026-10-08. **Status:** research note, not a decision. **Feeds:** [spec 06](../tier0/specs/06-save-replay.md), [spec 28](../tier0/specs/28-pop-levels.md), [spec 25](../tier0/specs/25-chronicle.md), [spec 27](../tier0/specs/27-detail-levels.md), [focus and compression](../design/focus-and-compression.md), [0045](../decisions/0045-open-questions-answered-2.md), [0002](../decisions/0002-engine-stack.md). **Evidence:** primary sources read from git clones (format specs, headers and READMEs of zstd, lz4, Parquet, Arrow, protobuf, CRoaring, FastPFor, simdcomp, Beringei, Luanti); our own code read at commit 8295162; every number on our data measured by us (machine and commands in section 3). Browser support for `DecompressionStream` is from search summaries only. Papers (Gorilla VLDB 2015, Lemire and Boytsov 2012, Roaring 2018) were not read; their algorithms were read in code or in the format specs that cite them. **IDs:** DC.

Spec 06 says saves are versioned and hashed; 0045 picked zstd "about level 3" for the Tier 1 container without measuring it; the replay viewer drops frames to fit a page. This note reads the formats, measures what our own saves, traces and pop records compress to, and proposes one format for all of them.

## 1. What the sources say

**Codecs.** zstd is the documented, RFC-backed default of every modern column format we read (Parquet, Arrow) and of Luanti's world files (DC-12, DC-13, DC-18). Its decoder speed hardly moves with the level, so the level trades only write time against size (DC-4). LZ4 is the fast-decode option. Parquet's deprecated LZ4 codec is the cautionary tale: a codec wrapped in undocumented framing became incompatible between implementations (DC-12), so we use the documented frame and nothing homemade around it.

**Determinism.** Compressed bytes are reproducible only for the same library version, build flags, parameters and thread mode (DC-5, DC-27). Our golden hashes must never see compressed bytes. The state hash is already taken over the uncompressed state (DC-38), so compression can be added under it without touching any golden.

**Transforms before the codec.** Every columnar system we read (Parquet, Arrow, Luanti's node arrays, Gorilla) stores like values together and turns slowly changing values into small numbers before a general codec or bit-packer sees them: deltas, delta of deltas, XOR with the previous float, zigzag, varint, bit width per block (DC-9, DC-10, DC-14, DC-17, DC-18). The SIMD integer libraries go faster still but define no format and check no input (DC-16), so they are a later optimisation behind our own framing.

**Sets of ids.** Roaring keeps a sorted array while a 2^16 chunk is sparse and a bitmap when it is dense, with a portable format (DC-15). For workplace-sized rosters a sorted delta-varint list is just as good. Roaring matters for region-sized membership queries.

## 2. What our data looks like

| Data | Raw | Best general codec | With a column transform first |
| --- | --- | --- | --- |
| World save, day 14 | 212,922 B | 20,531 B (zstd 3) | Event log 8,175 → 5,169 B (DC-28) |
| 47 hourly saves | 7.9 MB | 607 KB independent | 49 KB as deltas against the previous hour (DC-24) |
| Replay trace, 14 days | 18.8 MB | 167 KB (zstd 1) | Frames 180 → 19 KB; fields 5.6 → 2.1 KB (DC-30) |
| Pop registry, 1M pops | 5.06 MB | 1.73 MB (zstd 3) | Records 453 → 185 KB; founder specs 1,236 → 908 KB, or 0 if regenerated (DC-34, DC-36, DC-37) |

Three readings:

1. **Saves compress 10-12× with zstd 3 for a fraction of a millisecond** (DC-22, DC-23). The unchanged map and items are 58% of the raw save but only about 3.6 KB once compressed (DC-20, DC-21). Rule 7 (store only what diverged) matters for memory, load time and hashing more than for disk.
2. **Time is where the size is.** Each hour's save differs from the last by about 1 KB once compressed (DC-24). Any history of states (autosaves, rewind, a replay with keyframes) should be stored as keyframes plus deltas, not as full snapshots.
3. **Rows of mixed fields compress poorly; columns of like values compress well.** The gain is 1.6× on the event log, 2.4× on records and 9.5× on trace frames (DC-28, DC-30, DC-34). Floats should be integers or fixed point before storage (DC-30, DC-35), as spec 01 already makes quantities integers.

## 3. How it was measured

- **Machine:** cloud container, Linux 6.18, Intel Xeon @ 2.80 GHz, 4 cores; zs built `cmake --preset release -DZS_BUILD_WINDOW=OFF` with GCC at commit 8295162. Python 3 with `zstandard` 0.25.0 (libzstd 1.5.7) and `lz4` 4.4.5 (liblz4 1.9.4) from PyPI.
- **Data:** `zs --run --seed 1 --trace run1.json` (18.8 MB), `zs --stage6 --seed 1 --trace s6.json` (3.0 MB), `zs --days 14 --seed 1 --save days14.sav` (3,249 B; the stage-1 demo world, too small to matter). The one-world saves came from a scratch harness, kept out of the repo, that builds `zs::gen::make_world(1)` (as the window does), steps it, and calls `World::save()` every game hour for two days and at days 1, 3, 7 and 14. The pop registry save came from a second harness that builds 1M founders in cohorts of 500 with keyed ages and sexes, 2,000 cohort effects and 100,000 promotions (95,067 distinct; one in ten with an office, one in three with a death-year exception), then calls `PopRegistry::save()`.
- **Speeds:** single-threaded, best of N runs through the Python bindings, so they include call overhead and understate the C speed on small inputs. Ratios are exact. All round trips were checked byte for byte.
- **Column transforms:** written in Python for the measurement only. Each column is delta-coded against the previous row, zigzagged, written as LEB128 varints and concatenated, then zstd runs over the result. Python timings of the transforms are not reported.

## 4. What this means for us (Proposal)

1. **Compression is a transport layer under the canonical bytes.** The save, the state hash, the text twin (spec 06 rule 12) and the golden tests stay defined on uncompressed bytes. Nothing compressed is ever hashed or pinned (DC-5, DC-27, DC-38). The container header gains a codec id, a codec level (informational), the uncompressed size, and the hash of the uncompressed state. That is save format version 4, and an older uncompressed version still loads.
2. **One codec: zstd, vendored.** zstd is BSD-licensed, a single C library, RFC 8878 and readable by every tool we use. Vendor one pinned release under `third_party/` (0002 lists proven libraries). Its decoder reads any older frame, and a change of encoder output between versions is harmless under item 1. lz4 is not needed now (DC-41).
3. **Levels:** zstd 3 for a player save; zstd 1 for autosaves and traces (as small as 3 on our data, DC-22 and DC-29, and faster); zstd 19 only for an offline archive or a shipped scenario. Content checksum on (4 bytes, DC-26). Single-threaded, so the bytes do not depend on the machine's core count (DC-27).
4. **Tier 1 container (0045, SQLite):** one zstd frame per chunk or record blob. If blobs are under about 16 KiB, train one dictionary per blob kind (chunk, record, roster) offline from seeded runs and keep it in `data/` with an explicit dictionary ID. The save records which IDs it used, and a dictionary file is never changed once shipped (a new one gets a new ID). Expect about 16% from it, not more (DC-25).
5. **Columns inside blobs** for anything stored as many like rows: the event log, the scheduler queue, pop records, rosters, chronicle entries. Delta + zigzag varint per column, with fixed-point integers instead of doubles, then zstd (DC-28, DC-34, DC-35). Sorted id sets as delta-varint lists; Roaring only when a set is region-sized (DC-15).
6. **History as keyframe + deltas.** Autosave slots, a future time scrub and the replay's scrubbing points store one full compressed save per game day and an hourly delta compressed against the previous state (about 1 KB an hour, DC-24). Replay itself stays start state + seed + input log (spec 06 rule 2). Use `ZSTD_c_deterministicRefPrefix` if two writers ever have to produce the same delta bytes (DC-5).
7. **Regenerate rather than store.** Founder specs, the generated map and item placements are regenerated from seed + generator version + data hash, and only diffs are stored (spec 06 rule 7; DC-20, DC-37). This needs the generator version and data hash in the header, which spec 06 rule 4 already asks for.
8. **Traces:** in the short term, `embed.py` embeds the gzip of the full trace in base64 and the page decodes it with `DecompressionStream("gzip")`, instead of dropping frames (DC-31, DC-32). Later, `--trace` writes a binary columnar trace (frames as delta columns, fields as deltas per hour, about 21 KB for 14 days; DC-30) with a small decoder in the viewer.
